# ADR: issues のフォーマットと取り扱い

## ステータス

承認済み（Accepted）

## コンテキスト

`docs/podhmo/issues/` ディレクトリには、実装タスク・リファクタリング・調査などの作業単位を記録するファイルを置く。
これらのファイルは LLM エージェントへの指示書を兼ねており、「何を・なぜ・どのように対応するか」を構造化して記述する。

作業状態（未着手・完了待ち・完了）をディレクトリ構造で表現し、issue の検索・参照・整理を容易にする必要がある。

## 決定

### ファイル名規則

```
issue-NNN-<slug>.md
```

- `NNN` は 3 桁ゼロ埋め連番（001, 002, …）
- `<slug>` は内容を表す英小文字・ハイフン区切りの短い識別子

### ディレクトリ構成

```
docs/podhmo/issues/
├── issue-NNN-<slug>.md   ← 未着手・作業中
├── pending/
│   └── issue-NNN-<slug>.md   ← 作業完了、追記済み（マージ待ち等）
└── closed/
    └── issue-NNN-<slug>.md   ← 完全に完了・クローズ済み
```

### issue ファイルのフォーマット

#### 作業前（未着手・作業中）

```markdown
# <タイトル>

Created: YYYY-MM-DD

## 概要

何をするか（1〜3 文）

## 根拠

なぜこれが必要か

## 対応方針

- 具体的な手順や変更箇所
```

#### 作業完了後（closed / pending へ移動する前に追記）

```markdown
# <タイトル>

Created: YYYY-MM-DD
Completed: YYYY-MM-DD
Model: <使用モデル名>

## 概要

何をしたか（1〜3 文）

## 根拠

なぜこれが必要か

## 対応方針

- 具体的な手順や変更箇所（変更なければ削除可）

## 解決方法

実際にどのように解決したかを記述する。
予定と異なった点や考慮事項があれば合わせて記述する。
```

### ライフサイクル

1. **作成**: `docs/podhmo/issues/issue-NNN-<slug>.md` を新規作成
2. **着手**: ファイルはそのままの場所で編集
3. **完了**: `Completed`, `Model`, `## 解決方法` を追記した上で `closed/` または `pending/` へ移動
   - **closed**: 実装・マージが完全に完了したもの
   - **pending**: 実装は完了したが追加の確認・作業が残っているもの（マージ待ち、レビュー待ち等）

## 理由

1. **状態の可視化**: ディレクトリ位置だけで issue の状態がわかる。`ls issues/` で未着手一覧、`ls issues/closed/` で完了一覧が得られる。
2. **LLM への指示書としての明確性**: `概要`・`根拠`・`対応方針` の 3 セクション構成により、エージェントが「何を」「なぜ」「どうやって」を迷わず読み取れる。
3. **完了記録の保持**: `解決方法` セクションで実際の対応内容を残すことで、後から変更の意図を追跡できる。
4. **番号による参照**: `#NNN` 形式で他ドキュメントから issue を参照しやすい。

## 影響

- 既存の `issues/` 内ファイルは現フォーマットに概ね沿っているため移行コストは低い
- 完了済みタスクは順次 `closed/` へ移動する
- LLM エージェントは issue 作業完了時に `## 解決方法` を追記し、`closed/` または `pending/` へ移動することを原則とする
